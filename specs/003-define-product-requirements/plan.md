# Implementation Plan: PitterOmat v2 product requirements

**Branch**: `003-define-product-requirements` | **Date**: 2025-10-20 | **Spec**: [spec.md](./spec.md)

## Summary

Deliver the venue-ready LichtLoser experience across all 12 ESP32 displays and the Arduino-driven LED ring by formalizing Idle -> Menu -> Game flows, Quickstart replay, admin-governed ambience controls, and debug tooling. Work now targets a unified **Arduino Core** toolchain (ESP32 + AVR) with shared libraries, LVGL screen assets, WiFi coordination, constitution-compliant LED safety enforcement, and measurable usability reviews for operator-facing text.

## Technical Context

**Language/Version**: C++ (Arduino Core for ESP32 v2.x, Arduino AVR Core 1.8.x), Python 3.11 for tooling scripts  
**Primary Dependencies**: Arduino Core for ESP32, Arduino AVR Core, LVGL 8.x Arduino port, ArduinoJson, AsyncUDP (ESP32), manifest_tool Python package  
**Storage**: SD card (FATFS) for manifests/config, SPIFFS fallback for ESP32 session cache  
**Testing**: Bench sketches and loop-back diagnostics uploaded via Arduino IDE/CLI, Python-based manifest validation, manual QA per quickstart  
**Target Platform**: Waveshare ESP32-S3-Touch-LCD-4 (master + 11 slaves) and Arduino Mega 2560 via MAX485  
**Project Type**: Embedded multi-controller system (master-slave displays + LED controller)  
**Performance Goals**: Idle -> Menu transition <= 3 s, inter-display drift <= 100 ms, WiFi broadcast latency <= 20 ms, Quickstart relaunch <= 5 s  
**Constraints**: LED brightness <= 55%, display brightness 10-100%, admin auto-lock 10 +/- 1 s, Joker active only at 5 players, WiFi for ESP-to-ESP communication, RS485 for ESP-to-Mega  
**Scale/Scope**: 12 coordinated displays, up to 6 concurrent players, single cabinet deployment scaling to multiple venues post validation

## Constitution Check (Gate 1)

- **Principle I**: Use manifest_tool to validate SD assets; Quickstart/session persistence writes update associated manifest entries before release.  
- **Principle II**: Options and session entities follow shared schemas (see `data-model.md`); admin edits enforce compatibility (e.g., Joker guard).  
- **Principle III**: Hardware smoke suites reuse vendor demos from `TREIBER/` and archive logs into `tests/succeeded/` after each subsystem run.  
- **Principle IV**: Seat mapping pulls from `pitteromat.txt`; LED cap enforcement and Joker behavior traced through FR-004/007 and success criteria.  
- **Principle V**: Master ESP orchestrates UDP broadcast plus TCP acknowledgement; admin PIN workflow locks in 10 s; sync status surfaced in UI.  
- **System Architecture Directives**: Plan keeps WiFi between ESPs, RS485 to Mega, LVGL exports under `firmware/esp32/ui/`, and honors wiring baseline.  
- **Development Workflow & Test Lifecycle**: Phase plan includes manifest validation, hardware smoke loops, and documentation updates before release.

### Phase 2 - Implementation Planning (Current)
1. **Firmware Libraries (Arduino Core)**
   - Introduce shared Arduino libraries under `firmware/esp32/src/lib/` for sync messaging, brightness guard, and session storage.
   - Provide corresponding AVR-side helpers in `firmware/arduino/mega_led_controller/lib/`.
   - Persist session data using SPIFFS for ESP32 and mirror to SD manifest entries.
2. **WiFi & RS485 Coordination**
   - Implement AsyncUDP broadcast + acknowledgement handlers within Arduino sketches.
   - Maintain RS485 commands using `HardwareSerial` interfaces on both platforms.
3. **User Interface (LVGL on Arduino)**
   - Extend LVGL screen definitions (compiled via Arduino LVGL bindings) for Idle/Menu/Admin/Debug flows.
   - Wire input events through Arduino touch callbacks.
4. **Diagnostics & Safety**
   - Add brightness clamp enforcement and energy saver timers in Arduino sketches.
   - Provide diagnostic sketches (bench tests) for clamp, latency probes, LED diagnostics, and Quickstart flow.
5. **Documentation & Evidence**
   - Update quickstart instructions for Arduino IDE/CLI deployment on ESP32 and Mega.
   - Archive bench test logs and readability approvals.

*Exit Criteria*: All constitution principles verified through tests or documentation, quickstart checklist executed, and `/speckit.tasks` ready for detailed work breakdown.

### Risks & Mitigations
- **WiFi congestion**: Provide configurable resend window and instrumentation in debug overlay; fall back to TCP for critical actions.  
- **LED thermal load**: Clamp brightness in firmware and log attempts to exceed 55% for audit.  
- **Admin misuse**: Auto-lock timer plus audit trail for changes (store `updatedAt` in config bundle).  
- **Debug overlay leakage**: Auto-hide on new session start (captured in data model and success criteria).

### Milestones
1. **M1 - Sync Core Ready**: UDP/TCP channels operational, displays stay within drift budget.  
2. **M2 - Admin Workflow Complete**: PIN gate, ambience controls, ticker editing, and persistence verified.  
3. **M3 - Gameplay Validation**: LichtLoser spin, Joker logic, Quickstart replay all pass QA.  
4. **M4 - Release Candidate**: All tests archived, documentation updated, readiness for `/speckit.tasks` and implementation kickoff.
